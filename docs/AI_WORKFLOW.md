# Пиратские сокровища 2 — протокол разработки Codex ↔ Claude Code

Статус: согласовано капитаном и ChatGPT. Проект: `tixzeo/pirate-treasures2`.

## 1. Роли и источник истины

- **Капитан (владелец игры)** принимает продуктовые решения, тестирует сборки и разрешает объединение значимых изменений.
- **ChatGPT** помогает с приоритетами, геймдизайном, архитектурой, техническими заданиями и независимым разбором PR. Не считать его отзыв автоматическим одобрением мержа.
- **Дежурный разработчик** — либо Codex, либо Claude Code — отвечает за реализацию, ветку, тесты, PR и передачу контекста.
- **Второй разработчик** выполняет независимое ревью, проверяет риски и предлагает правки. По умолчанию **не меняет файлы дежурного одновременно**.
- **GitHub** — источник истины для исходников и истории изменений. Актуальные решения по продукту фиксируются в живой дорожной карте Claude Doc; после согласования синхронизируются с `docs/ROADMAP.md` в репозитории. Если документы расходятся, уточнить у капитана, а не угадывать.

## 2. Чередование 3/3

1. **Три календарных дня Codex — главный**, Claude Code — ревизор.
2. **Следующие три календарных дня Claude Code — главный**, Codex — ревизор.
3. Далее повторять. Конкретные даты начала и окончания фиксировать в `docs/HANDOFF.md`; не выводить смену из даты последнего коммита.
4. **Смена не обрывает мелкую начатую задачу**: текущий главный завершает ближайший безопасный атомарный этап (код + тесты + отчёт) либо передаёт незавершённое в отдельной ветке как WIP. Продление фиксируется в журнале; крупный этап нельзя бесконечно задерживать под видом «мелкого».
5. Если срок смены наступил посреди крупной задачи, не продолжать без согласования. Остановиться на безопасной точке, оставить ветку и отчёт, передать следующему.
6. Внеплановые критические исправления допускаются с уведомлением капитана и обязательной записью в журнале.

## 3. Правила Git

- **Не работать напрямую в `main`.** По решению капитана от 2026-10-25 собирать примерно **10–20 выполненных задач в один общий PR** в ветке пакета (`codex/<batch>` или `claude/<batch>`). Группировать задачи по теме (например, «острова» или «бой»). Одна задача — один коммит; каждый коммит проходит доступные тесты и сборку. В PR вести общий чек-лист результатов. Отдельный PR на каждую мелкую задачу не требуется.
- Перед началом проверить актуальность `main`, статус рабочего дерева, открытые PR и журнал передачи.
- Один ответственный за конкретные файлы/подсистему в рамках задачи. Не запускать параллельную запись двух агентов в одну рабочую директорию/ветку.
- Небольшие логичные коммиты, понятные сообщения; без смешивания несвязанных фич.
- Открывать общий PR с описанием цели пакета, чек-листом выполненных и оставшихся задач, результатов тестов, рисков, скриншотов/видео при изменении графики. Ревизор проверяет этапы внутри PR; размер пакета не отменяет проверки и не требует откладывать исправление регрессии до накопления 10 задач.
- **Мерж в `main` только после ревью и решения капитана** для заметных изменений геймплея, визуала, баланса и архитектуры. Отсутствие замечаний от агента само по себе не означает одобрения.
- Нельзя без явного согласия делать force-push в общие ветки, удалять чужие ветки, переписывать историю, отключать тесты, массово удалять ассеты или менять секреты.

## 4. Начало каждой смены

Дежурный разработчик:

1. Читает `docs/AI_WORKFLOW.md`, `docs/HANDOFF.md`, `docs/AUDIT.md`, `docs/ROADMAP.md` и актуальные PR.
2. Проверяет фактическое состояние репозитория; отличает **реализовано**, **в PR**, **запланировано** и **гипотеза**.
3. Кратко сообщает капитану и ChatGPT: текущая ветка/коммит, незавершённые задачи, риски и одну следующую атомарную задачу.
4. Получает/подтверждает критерии приёмки, после чего начинает изменения.

## 5. Стандарт выполнения задачи

**До работы:** цель; границы задачи; затронутые модули; зависимости; критерии готовности; тест-план; риски для мобильной версии.

**Во время:** не ломать действующие механики ради визуала; придерживаться соглашений об именах частей моделей и масштабе; проверять управление кораблём, швартовку, бой, камеру, «три в ряд» и производительность при релевантных изменениях. Не заявлять «проверено», если тест фактически не выполнялся.

**После:** запустить доступные проверки (указать точные команды и результат), создать PR и запросить ревью второго агента. Для визуальных задач предоставить скриншоты/видео; для производительности — устройство, сцену и измерения. Если запуск невозможен, прямо указать причину и что осталось непроверенным.

## 6. Независимое ревью второго агента

Проверить:

- Соответствие ТЗ и критериям приёмки; нет ли неоговорённых побочных изменений.
- Ошибки, краевые случаи, регрессии в механиках и сохранениях.
- Координаты, масштаб, коллизии, привязки к движущемуся кораблю, камера, ввод ПК/Android — если затронуты.
- Производительность и размер сборки — если затронуты.
- Качество тестов, ясность PR и возможность отката.

Вердикт: **APPROVE / CHANGES REQUESTED / NOT VERIFIED** с конкретными аргументами. Второй агент даёт рекомендации, **не мержит сам** и без согласования не переписывает чужую реализацию.

## 7. Протокол передачи смены

Передающий разработчик обновляет `docs/HANDOFF.md` (шаблон ниже), фиксирует коммиты и ссылки на PR и передаёт следующему разработчику:

- Сделано и реально проверено.
- Не закончено: точный статус и следующий шаг.
- Открытые PR, ветки, коммиты; нет ли незакоммиченных файлов.
- Команды тестов, результаты, известные ошибки и регрессии.
- Риски для игрового процесса, графики, мобильных устройств и ассетов.
- Какие решения требует капитан; что нельзя менять без согласования.

Принимающий разработчик сверяет журнал с GitHub, воспроизводит основные проверки и подтверждает приём. При несовпадении состояния репозитория с журналом останавливается и уточняет, а не «исправляет на глаз».

## 8. Приоритет ближайшего этапа: шлюп 22 м — техническая основа первого класса

Утверждена прогрессия игрока: **шлюп 22 м → бриг 32 м → галеон 46 м**, каждый со своей геометрией и планировкой. Текущий [PR #6](https://github.com/tixzeo/pirate-treasures2/pull/6) — **двухмачтовая 22-метровая техническая основа для будущего шлюпа**, а не финальный шлюп. Не переименовывать старую модель в шлюп и не считать её однопарусной: для стартового класса нужен отдельный одномачтовый GLB.

Приоритет по коду — безопасная приёмка PR #6, сохранение швартовки, боя, камеры, корректных поверхностей и препятствий. Палуба текущего прототипа 4,4 м; свободные маршруты 1,5–2 м надо подтвердить с коллайдером персонажа (~1,75 м), каюта и лестница пока не решены. Сначала прототип ходьбы и удобство прохождения, затем финальная геометрия и декор. Никакого масштабирования всех кораблей и босса общей цифрой.

**Босс «Каракатица» остаётся 15 м** как ранний сюжетный противник. Новые уровни и крупные корабли игрока получат отдельные классы врагов и боссов; уровень противника не должен автоматически повышаться только из-за корабля игрока. Причал 28,8 м — ограничение для крупных классов; предусмотреть большие порты/рейдовые стоянки. Подробности: `docs/FLEET_DESIGN.md` и `docs/ROADMAP.md`.

Параллельно с развитием масштаба снять и сохранять базовые FPS/draw calls/память на ПК и телефоне. Любые выводы о мобильной производительности подтверждать измерениями.

## 9. Запрет на фиктивные результаты

Запрещено отмечать задачу завершённой без подтверждения: коммита/PR, реальных тестов и проверки игрового поведения капитаном там, где она необходима. Все оценки времени приблизительные. Если инструмент не имеет доступа, это прямо указать, не имитировать результаты.
